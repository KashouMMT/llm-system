## 2. 【A】ご決定いただきたい事項

仕様書上で未確定、または記載のない事項です。ご決定いただかないとスケジュールを確定できません。

### A-1. 開発方式とデモ頻度（第13章）

第13章にMVP1〜4およびExpansionの区分はございますが、進め方の定義がございません。

- デモ（動作確認）のご希望頻度をご教示ください（各フェーズ完了時 / 2週間ごと 等）
- 開発方式について、2週間スプリント（アジャイル）とウォーターフォールのいずれで進めるかご決定をお願いいたします

いずれの方式でも実装内容は変わりませんが、ご報告の頻度と仕様変更への対応方法が異なります。

### A-2. MVPの実施順序（第13章）

現行の順序は MVP1（求人検索）→ MVP2（保存条件・新着通知）→ MVP3（書類作成）となっております。順序の入れ替えについてご相談させてください。理由は以下の2点です。

- **書類作成機能（MVP3）は求人データ取得基盤に依存しません。**求人データの取得は本プロジェクトで最も不確実性が高い部分であり、取得元の仕様確認や技術検証に時間を要する可能性がございます。仮にMVP1が遅延した場合でも、MVP3は並行して進行でき、動作するものを継続してご確認いただけます
- **MVP2とMVP3は共通してメール送信基盤を必要とします。**基盤を先行して構築するか、順序を入れ替えるほうが効率的です

なお現時点の実装状況として、AIによる聞き取りおよび書類内容の文章生成については試作段階のものがございますが、**ファイル出力（PDF・Word等）、書類のアップロード、記載内容の抽出、利用者による確認画面、メール送付についてはいずれも未実装**です。第5章の機能全体としては、新規開発が必要な範囲が大半を占めます。

技術的にはいずれの順序でも実現可能ですので、ご意向をご確認いただければと存じます。

### A-3. 決済代行サービス（第7章）

第7章に「Pricing plans, free-tier scope, payment provider, and cancellation rules will be finalized separately」との記載がございます。

- ご指定の決済代行サービスはございますか。特にご指定がなければStripeを想定しております
- 料金プラン・無料範囲・解約規定が未確定の場合、課金機能を後半のMVPに配置することをご提案します

### A-4. 履歴書・職務経歴書の様式（第5章）

ベースとする様式をご指定ください。JIS様式例は2020年に廃止され、現在は厚生労働省の標準的な様式が中心となっておりますが、複数の様式が流通しております。

複数様式への対応も可能です。様式は雛形ファイルとして用意する方式のため、追加は比較的軽微な作業です。

### A-5. 想定同時接続ユーザー数（記載なし）

リリース時に想定される同時接続ユーザー数の目安をご教示ください。サーバー構成・性能目標・費用見積の前提となります。

### A-6. ステージング環境・ドメイン（記載なし）

検証用環境および本番ドメインは貴社よりご提供いただけますでしょうか。弊方でご用意する場合は費用とリードタイムが発生いたします。

### A-7. 利用規約・プライバシーポリシーの作成担当（第12章関連）

氏名・連絡先・職務経歴等の個人情報を取り扱い、かつ有料サービスを提供するため、利用規約およびプライバシーポリシーが必要となります。作成のご担当をご確認ください（弊方の作業範囲外と想定しております）。

## 3. 【B】技術面からのご提案

以下は**仕様書に記載のある内容の変更をともなうご提案**です。ご承認いただける場合は最終仕様書に反映いたします。

### B-1. OCRの対応範囲を限定（第5章・第10章）※スコープ変更

現行仕様では第10章に「OCR / image analysis」、MVP3に「OCR-assisted entry」の記載がございます。

**ご提案:** 現時点ではOCRを必須要件とせず、対応範囲を**スキャンされたPDF**に限定することをご提案します。

技術的背景として、PDFには2種類ございます。

| 種別 | 内容 | OCRの要否 |
|---|---|---|
| テキスト埋め込みPDF | 文字情報が埋め込まれている | **不要**（直接読み取り可能） |
| スキャンPDF | 紙面を画像として保存したもの | 必要 |

多くの履歴書・職務経歴書は前者のため、OCRなしで対応可能です。画像形式（JPEG / PNG）および手書き書類への対応は、精度が安定しないため将来の拡張とさせていただくことをご提案します。

### B-2. Career Advancement Assessment をExpansionへ移動（第16章）※スコープ変更

**ご提案:** 第16章のCareer Advancement Assessmentを、初期MVPではなくExpansion（拡張フェーズ）での実装とすることをご提案します。

理由は依存関係にございます。本機能は仕様書の記載どおり「利用者が履歴書・職務経歴書を完成させた後」に動作し、かつ管理者による確認・編集フローを前提としております。したがって**書類作成機能と管理画面の双方が完成していなければ動作しません。**技術的に先行して実装することができない構成です。

なお本章は章番号が第10章と重複しております。あわせて修正をご提案いたします。

### B-3. SNSからの求人情報取得を初期スコープから除外（第3章）※スコープ変更

**ご提案:** SNSからの求人情報取得については、各プラットフォームのAPI仕様・利用規約・取得可能範囲・費用等の制約を確認する必要があるため、**初期スコープから除外し将来の拡張**とすることをご提案します。

技術的な確認結果として、Facebook / Instagram / LinkedIn については、第三者による公開投稿の横断検索手段が提供されておりません。X（旧Twitter）については取得手段が存在しますが、該当機能を含む上位プランが必要となり、費用および取得データの性質について別途精査が必要と考えております。

仕様書第14章にも各プラットフォームの調査が検証項目として挙げられておりますので、その結果を待って判断する形をご提案します。

### B-4. 有人対応チャネルをアプリ内チャットに限定（第6章）※未確定事項の確定

第6章に「Supported channels will be finalized during development」との記載がございます。スケジュール確定のため、初期リリース時点のチャネルを確定させていただきたく存じます。

**ご提案:** 初期リリースでは**アプリ内チャット**に限定し、LINE連携は将来の拡張とすることをご提案します。

理由として、LINE連携にはLINE公式アカウントの開設、Messaging APIの設定、アカウント認証、および**Webサービス側の利用者アカウントとLINEアカウントの紐付け機能**が必要となり、設定作業ではなく一つの機能として開発が必要となるためです。

なお、アプリ内チャットであれば利用者が既に利用中の画面上で有人対応者が応答できるため、既存の会話基盤を活用でき、追加開発を最小限に抑えられます。

### B-5. 管理画面の段階的構築（第8章）※実装方針

**ご提案:** 第8章の管理画面8機能を一括で構築するのではなく、各MVPと並行して段階的に構築することをご提案します。

| 構築時期 | 機能 |
|---|---|
| 前半MVP | ユーザー一覧、ユーザー詳細 |
| 中盤MVP | FAQ管理、未回答質問、求人取得状況 |
| 後半MVP / 拡張 | メール履歴、課金管理、監査・セキュリティ |

各MVPで必要となる管理機能のみを構築することで、早期に運用を開始でき、仕様変更にも対応しやすくなります。

### B-6. 求人データの取得頻度と鮮度確認（第3章・第11章）※仕様の明確化

仕様書では新着監視が1日1回と定義されておりますが、**求人データそのものの取得頻度**、および利用者へ提示する時点で当該求人が有効であることをどのように確認するかについて、記載がございません。

**ご提案:** 以下の3つの動作を区別して定義することをご提案します。

| 動作 | 実行時期 | 対象範囲 |
|---|---|---|
| **一括取得** | 週次・定期実行 | 登録済みの全取得元。利用者の保存条件に該当する取得元は優先的に高頻度で実行 |
| **鮮度確認** | 検索時 | 利用者へ提示する直前の求人のみ。かつ前回確認から一定時間が経過しているものに限定 |
| **手動取得** | 管理者による実行 | 指定した取得元を対象に、バックグラウンド処理として実行 |

**鮮度確認について。** 求人を提示する前に、当該求人が現在も掲載中であるかを確認いたします。対象は実際に提示する求人のみ（通常10件未満）に限定されるため、外部サイトへのアクセス量は検索対象の規模ではなく提示件数に比例し、予測可能な範囲に収まります。掲載中であることが確認できない求人は、提示対象から除外するか、その旨を明示いたします。

なお、確認はHTTPの応答コードのみでは判定できない点を申し添えます。求人サイトの多くは掲載終了後も通常の応答を返し、掲載終了である旨をページ本文にのみ記載するためです。したがって取得元ごとにページ内容を確認する処理が必要となり、小規模ではございますが開発項目として発生いたします。

**採用しない方式について。** 利用者のご質問を契機として、その場で外部サイトから求人データを取得する方式は採用いたしません。外部サイトをリアルタイムに検索する構成では応答時間が不安定となり、また外部サイトへのアクセス量が利用者の行動によって変動し、制御できなくなるためです。データの取得はあくまで定期実行および管理者による管理下に置き、**検索時に行うのは既に保有している求人の有効性確認であり、新規求人の探索ではございません。**

この区別は、データ取得と検索を分離し、AIには求人データベースの検索機能のみを与えるという、以前ご提出した資料の方針と一致しております。

**第11章との関連。** 仕様書には既に「取得・更新日時により古い求人の鮮度を可視化する」旨の記載がございます。上記の鮮度確認とあわせて、提示する各求人に取得日時を標準で表示することをご提案します。

## 4. 【C】仕様書への追記のご提案

現行の仕様書に記載がなく、実装上必要となる項目です。

### C-1. 通知機能を独立した章として追加

現在、通知に関する記載が新着求人通知（第2-3章）、メールサービス（第10章）、有人対応（第6章）に分散しております。通知機能として独立した章にまとめることをご提案します。

対象: 新着求人通知、生成書類の送付、有人対応の返信通知、システム通知、将来のLINE連携

あわせて以下の仕様を明確化する必要がございます。

- 1日1回の通知を実行する時刻
- 新着が0件の場合に通知を送信するか否か
- 通知の失敗時の再送処理（第12章に再試行の記載はございますが、詳細が未定義です）

### C-2. アカウント関連機能の追記

第7章は「registration and login」の記載のみですが、実運用には以下が必要となります。いずれも実装工数が発生いたします。

- パスワード再設定
- メールアドレス確認（登録時の認証）
- 退会処理およびデータ削除

### C-3. 求人データの重複排除に関する仕様の明確化（第4章・第11章）

第11章に「Deduplicate the same job appearing on multiple sources where feasible」との記載がございますが、データ構造としての定義が第4章にございません。

**ご提案:** 第4章の共通項目に、取得元ごとのIDと、統合後の求人IDを区別する構造を追記することをご提案します。同一求人が複数サイトに掲載されている場合、1件の求人として統合し、取得元を複数保持する形となります。

本項目は本プロジェクトにおいて**技術的難易度・工数ともに見積が最も難しい箇所**です。同一求人であっても、サイトごとに求人ID・求人タイトル・企業名表記・給与の表記単位（月給／年収）・本文がそれぞれ異なるため、機械的に同一と判定する共通の手がかりが存在しないことが理由です。実データを確認するまで精度の見通しが立たないため、スケジュール上も余裕を見込む必要がございます。

### C-4. 取得元障害時の利用者への表示（第12章）

第12章に「If one source stops working or changes specifications, searches against other sources must continue」との記載がございますが、その際に利用者に何を表示するかの定義がございません。

例: 「現在一部の求人サイトからの情報取得に問題が発生しております」等の表示要否をご確認ください。

### C-5. 個人情報の保持期間（第12章）

第12章に保持・削除方針の必要性は記載されておりますが、**具体的な期間の記載がございません。**実装には具体的な日数が必要となります。

対象: アップロードされた履歴書・職務経歴書、生成された書類、会話履歴
