# llm-system

A conversational LLM system built on LangChain and LangGraph, with PostgreSQL-backed persistence and rolling summarization for long-running conversations. The model provider is selectable at startup (`LLM_PROVIDER`): a local Ollama instance, or any OpenAI-compatible endpoint (OpenAI, OpenRouter, Groq, DeepSeek). Runs as a CLI or a FastAPI server, with a React + TypeScript frontend in `ui/` that receives tokens over Server-Sent Events.

Its current application is Japanese job-application documents: the `anna` persona interviews the user for the facts a 履歴書 (rirekisho) and a 職務経歴書 (shokumu keirekisho) require, and one tool per document renders the confirmed data to a downloadable file attached to the assistant's message. Both render to the formats an employer actually receives — the 履歴書 as `.xlsx` filling a JIS-style form, the 職務経歴書 as `.docx` — built from client-approved reference documents in `documentation/other/`.

## Requirements

- Python 3.11+
- PostgreSQL (reachable instance; the app creates its database and tables on startup if they don't exist)
- One model provider: either [Ollama](https://ollama.com) running locally with the target model pulled, or an API key for an OpenAI-compatible endpoint
- Node.js 20+ (frontend only)

The summarization prompts are part of the prompt set: `app/prompts/<set>/summary_chunk_prompt.txt` and `summary_merge_prompt.txt`. `settings` resolves one copy at import from the env `SYSTEM_PROMPT`, but `SummarizationService` re-loads them per run from the runtime `system_prompt_name` (via `load_summary_chunk_prompt` / `load_summary_merge_prompt` in `app/llm/system_prompt.py`), so changing `system_prompt_name` at runtime swaps the summarization prompts along with the persona; the import-time copy is only the fallback if that read fails. A set is all-or-nothing — if that folder is missing or has an empty copy of `system_prompt.txt`, `summary_chunk_prompt.txt`, or `summary_merge_prompt.txt`, the loader logs a warning and falls back to `app/prompts/default/` for the entire set. The `default/` set itself must always be complete; an incomplete one raises at startup.

A set may also contain an optional `first_message.txt`. When present, its text is seeded as a complete `assistant` message when a conversation is created (resolved from the runtime persona, in the same transaction as the conversation), so the persona opens with a stated direction and the model sees that greeting as its own first turn. A set without the file simply opens with no greeting.

A set may also contain an optional `attachment_prompt.txt` — what this persona should look for in an uploaded file (Anna: dates and qualifications for her documents; Meguru: items, counts and materials). It is composed directly under the fixed attachments section from `app/attachments/prompts.py`, never instead of it, so no persona can drop the injection guard or the re-read rule. Like a persona file it is sent whatever plugins are loaded, so it must not name plugin tools or commands.

A set may also contain an optional `title_prompt.txt` — the instruction used to name a conversation from its first user message (`{message}` is substituted verbatim). A set without the file falls back to the built-in `DEFAULT_TITLE_PROMPT`, so titling keeps working everywhere; the file only exists to let a persona phrase its titles differently.

### Runtime settings

Most of the table above is a *default*, not a fixed value — 14 of those variables can be changed while the process is running, without a restart, and the change persists across restarts too. `DB_*`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_PROVIDER`, `FILE_STORAGE_DIR` and the other connection/provider settings cannot: they are bound into objects (a connection pool, an LLM client, a storage root) that are only built once, at startup.

| Tier | Behaviour | Examples |
|---|---|---|
| Runtime-editable, persisted | Change takes effect on the next turn; survives a restart (stored in `app_settings`) | `temperature`, `top_p`, `top_k`, `max_tokens`, `context_window`, `system_prompt_name`, `max_checkpoint_messages`, `max_context_history_messages`, `max_unsummarized_messages`, `min_retained_raw_messages`, `summary_token_threshold`, `max_summary_chars`, `sse_heartbeat_seconds`, `sse_queue_maxsize` |
| Runtime-editable, session-only | Change takes effect immediately; reverts to the environment on restart | `log_level` |
| Startup-only | Requires a restart | everything else in the table above |

In CLI mode, `/settings` lists every runtime-editable value and whether it is persisted, `/set <key> <value>` changes one, and `/reset <key>` restores its environment default. The CLI and the HTTP layer share three `Application` methods so behaviour cannot drift between the two front ends: `apply_settings()` (validate, apply, persist — the startup persisted-settings loader goes through it too), `reset_setting()` (restore one environment default and drop its `app_settings` row), and `describe_settings()` (the value / persisted / default view that both `GET /settings` and the CLI render).

## Architecture

**Composition root.** [app/runtime/application.py](app/runtime/application.py) (`Application`) is an async context manager that owns the lifecycle of every shared resource. `RuntimeSettingsHolder` is built first, from the environment, before the pool even opens — `EventBus` needs it at construction time. Once the pool is open, persisted overrides are layered on top of the environment defaults. `initialize()` then applies migrations, ensures the single `root` user exists, sweeps orphaned in-flight messages left by a previous crash, loads the system prompt, builds the LLM client, opens the LangGraph PostgreSQL checkpointer, and wires the context builders, `AgentGraph`, `EventBus`, `ConversationLock`, `SummarizationService`, and `ChatService`. `app/main.py` opens one `Application` and hands it to either the CLI loop or the FastAPI app, serving the API on the same event loop the pool was opened on, and catches `KeyboardInterrupt` at the top level so a second Ctrl+C during shutdown prints a message instead of a stack trace.

**Request flow — generation is decoupled from the HTTP request.** `POST /conversations/{id}/messages` persists the user message and an empty, `status='streaming'` assistant message immediately (`ChatService.begin_turn`), then returns `202` without waiting for a response. Generation runs as a background task (`ChatService.generate`) that streams tokens from `AgentGraph`, buffers them in memory, and publishes each one to an in-process `EventBus`. Any number of clients — including the sender — read the same stream via `GET /events`, an SSE endpoint; there is exactly one token path, so multi-tab consistency falls out of the design rather than being handled as a special case. The response is written to PostgreSQL exactly once, when generation reaches a terminal state (`complete` / `cancelled` / `failed`), which is also what makes a client disconnect harmless — nothing about the turn depends on an HTTP connection staying open. A per-conversation `ConversationLock` (in-process) rejects a second concurrent send on the same conversation with `409`, since the LangGraph checkpointer is keyed by conversation and two concurrent runs would corrupt it. Summarization is scheduled afterward as a background `asyncio.Task` and never blocks or can fail the chat response.

**Shutdown.** An SSE response never ends on its own — the client stays connected and the generator keeps emitting heartbeats — so uvicorn is given `timeout_graceful_shutdown=5` to cut whatever is still open. All detached work — generation, finalization writes, summarization — is spawned through `Application.spawn` into one task registry. `Application.shutdown()` drains that registry in two passes before closing the connection pool, waiting briefly and then cancelling: the first pass cancels the in-flight generations, and cancelling one runs its `finally` block, which spawns the finalization write *into the same registry*; the second pass drains those. A cancelled generation still persists its partial answer, so the pool has to outlive both passes. Whatever does not finish in time is caught by `sweep_streaming()` on the next startup.

**Authentication** (`app/authentication/`, `app/repositories/user_repository.py`, `app/repositories/session_repository.py`). Session-based, built in-house. `POST /auth/login` verifies an email and password, inserts a `sessions` row, and returns an opaque token (`secrets.token_urlsafe(32)`) in an `HttpOnly` cookie. `POST /auth/register` is public and creates a `user`-role account from an email and password — email is the unique identity, so one address is one account. It sets no cookie: registering and signing in are deliberately separate steps, so the client posts the same credentials to `/auth/login` next. The request models apply a deliberately loose email check (a non-empty local part, an `@`, a non-empty domain, no whitespace) rather than pulling in `email-validator` for RFC-perfect parsing — enough to reject typos while still accepting a bare host like `root@localhost`. Only the SHA-256 hash of the token is stored, so a database dump yields no usable sessions; resolution on each request is one indexed query joined to `users` with the expiry filter baked in. Passwords are hashed with argon2id (`argon2-cffi`); the unknown-email branch of login still runs one verification so response time does not reveal whether an account exists, and both verifications run in a worker thread so they do not stall the event loop that also serves the SSE streams. Roles are `user`, `admin`, and `root`, and a partial unique index (`WHERE role = 'root'`) makes "exactly one root" a database guarantee. The root user is seeded on startup from `AUTH_BOOTSTRAP_EMAIL` / `AUTH_BOOTSTRAP_PASSWORD` (the email defaults to `root@localhost`), or with a random password logged once if the password is unset, so the system is never left with no way in; `--seed-admin` resets the root credentials as the recovery path. Seeding inserts the row directly, so the email check on the login endpoint does not apply to it — but `root@localhost` satisfies that check anyway, so root can still sign in through the API. `current_user` and `require_admin` are FastAPI dependencies (`app/authentication/dependencies.py`, declared with `Annotated[...]` so the `Depends` call is not a mutable default): every conversation, message, and event route requires the cookie and is scoped to the owning user — a conversation belonging to someone else returns `404`, not `403` — and `PATCH` / `DELETE /settings` require an admin. **Account management is root's alone** (`require_root`, i.e. `can(user, ACTION_MANAGE_ADMINS)`): `GET/POST /users` and `PATCH/DELETE /users/{id}`, behind the settings page's ROOT → Users section. The rules live in `UserAdminService` (`app/authentication/user_admin.py`), not the handlers: only `user` / `admin` are assignable; the root account is listed but never edited or deleted there (its recovery path is the environment and `--seed-admin`, and a root that could demote itself could lock everyone out); a password change deletes that user's sessions; a role change needs nothing, since the session lookup re-reads the user row on every request. Delete is a hard delete. The `ON DELETE CASCADE` chain removes every row the account owns — sessions, conversations, messages, summaries, file rows, and any recycling evidence on those files. Two things have no foreign key and are cleaned up by the service instead, after the rows commit: LangGraph's checkpoint threads (`checkpoints` / `checkpoint_blobs` / `checkpoint_writes`, keyed by the conversation id as text — removed through the checkpointer's own `adelete_thread`, passed in as a plain callable so account code never imports LangGraph) and the files' bytes. `UserRepository.delete` reads both the conversation ids and the storage keys in the same transaction as the delete (rows first, the rest second, as in the orphan sweep). A "ban" that keeps the data and refuses the login is the intended long-term semantics. A refused change answers `404` / `409` / `422`, never `403`, because the SPA treats any `403` as a stale CSRF token and swaps the whole app for its reload screen. The CLI talks to `Application` directly rather than over HTTP, so it has no session; it loads the `root` user at startup and acts as it. A conversation also carries a lifecycle `status` (`active` / `held` / `closed`); `ChatService.begin_turn` refuses a non-admin send into a `held` conversation with `423`, a hook for a future admin-override feature that is otherwise inert.

CSRF is defended in two halves. `SameSite` on the session cookie is the browser-level half. The application-level half is `CSRFMiddleware` (`app/authentication/csrf.py`), a pure-ASGI gate — not a `BaseHTTPMiddleware`, so it never wraps the SSE response stream — that runs before the router on every non-safe method and applies three checks: (1) `Origin` (falling back to `Referer`) must be in `CSRF_TRUSTED_ORIGINS`, which is the only check that also covers `POST /auth/login` and `/auth/register` since no session token exists yet there; (2) the body's `Content-Type` may not be one a cross-site `<form>` can send (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`); (3) a signed double-submit token — the non-`HttpOnly` `csrf_token` cookie and the `X-CSRF-Token` header must be equal, and the token's HMAC (keyed by `CSRF_SECRET`) must verify against the caller's session token, so a `csrf_token` planted from a sibling subdomain cannot be forged into a valid one. The cookie is issued alongside the session cookie by `POST /auth/login` and re-issued by `GET /auth/me` — which the SPA calls on every load — so a restart-invalidated or pre-feature cookie repairs itself. `api/client.ts` reads the cookie and sets the header on every non-GET request. It is added *before* the CORS middleware in `create_api` so CORS stays outermost and a rejected request still carries the headers a browser needs to read the `403`.

**Runtime settings** (`app/config/runtime_settings.py`, `app/repositories/settings_repository.py`, `app/llm/sampling.py`). `RuntimeSettings` is a frozen dataclass; changing a value means swapping the whole instance (`RuntimeSettingsHolder.apply()`), never mutating a field, so a reader that has already taken its snapshot for the current turn cannot see a half-applied change. Consumers fall into two groups: some (`HistoryContextBuilder`, `EventBus`) hold the holder and read `.current` per use; the agent node and the checkpoint-compaction node instead take one snapshot at the top of each turn, since their settings are baked into objects built for that turn only (the model, the checkpoint limit). `FIELD_PARSERS` doubles as the allowlist — a key with no parser (`db_password`, `llm_api_key`, …) cannot be set through `apply()` by any caller, so there is no second list to keep in sync with the database or the `PATCH /settings` endpoint. Cross-field invariants (`max_tokens < context_window`, `max_unsummarized_messages ≤ max_context_history_messages`, `min_retained_raw_messages < max_unsummarized_messages`) live in `__post_init__` rather than in `apply()`, because `replace()` runs it: one implementation then covers both the runtime edit and the environment read at startup, and it raises *before* the new instance is assigned, so a rejected batch cannot leave a partially applied state behind. Persisted overrides live in the sparse `app_settings` table — one row per key that has actually been changed, so an unset key still falls through to the environment and resetting a setting is a `DELETE` rather than writing the default back; `log_level` is deliberately excluded from persistence, since it is the one lever that must still work from the environment or `--log-level` when startup itself is failing. `sampling.py` applies temperature/top_p/top_k/max_tokens/context_window to the LLM client via `.bind()` (never by rebuilding it, so a settings change cannot swap the client out from under a generation already streaming) — Ollama and OpenAI take different shapes: `ChatOllama` only reads these from its own constructor fields when assembling the request's `options` object, so they must be bound as a single nested `options={...}` dict rather than as flat kwargs, while `ChatOpenAI` accepts them as top-level kwargs directly.

**LangGraph agent** ([app/agent/graph.py](app/agent/graph.py)):

```
START → prepare_context → agent ─┬─(tool call)→ tools → agent
                                 └─(final answer)→ compact_checkpoint_state → END
```

- `prepare_context` (`app/agent/nodes/prepare_context_node.py`) runs `ConversationContextBuilder` once per request to assemble background context.
- `agent` (`app/agent/nodes/agent_node.py`) binds tools to the LLM and streams a response over `[system_prompt, prepared_context, current_turn_messages]`.
- `tools` is a LangGraph `ToolNode` over every tool the plugin loader found: `get_current_time`, `generate_rirekisho` / `generate_shokumu_keirekisho`, and `read_attachment`. `handle_tool_errors` routes a rejected call back to the model as a message naming the offending field, so a schema violation becomes a question to the user rather than a failed turn.
- `compact_checkpoint_state` (`app/agent/nodes/compact_checkpoint_state_node.py`) trims the LangGraph checkpoint history to `MAX_CHECKPOINT_MESSAGES` after a final answer, keeping checkpoint rows from growing unbounded.

State is checkpointed per conversation (`thread_id` = conversation UUID) via `AsyncPostgresSaver`.

**Tool plugins** (`app/plugins/`). The list of tools `AgentGraph` receives is never hand-assembled; `Application.initialize()` calls `load_tools()` once at startup and passes whatever it returns. A plugin is a *folder* directly under `app/plugins/` whose package exports a module-level `PLUGIN` (a `ToolPlugin`: a name, a factory function, a description, and an optional `command_factory` — see **Slash commands** below). `loader.py` walks that directory with `pkgutil.iter_modules`, considering packages only — never loose `.py` files, which is what lets `contracts.py` and `loader.py` sit beside the plugins without a skip list someone has to keep in sync — imports each one in sorted order (so the resulting tool list, which is prompt text, does not reorder itself between restarts for no reason and bust provider-side prompt caching), and calls its factory with one `ToolContext` carrying the shared dependencies a tool might need (`file_storage`, `file_repository`, `conversation_repository`, and the app's own model access: `chat_model`, the LangChain client `AgentGraph` already uses, and `llm`, an `LLMAccess` of `provider`/`base_url`/`api_key`/`model` for a plugin that wants to build its own raw SDK client instead — data only, never a client factory, and never logged — plus `db_pool`, the app's own async Postgres pool, for a plugin that owns tables; `reply_blocks`; and `agent_role`, the only path for SQL the model writes — see **Agent database role**). **A plugin that owns tables keeps everything database-related in its own `database/` folder** (DDL, repositories, later the grants to the agent's read-only role) and creates them from the optional async `ToolPlugin.initialize(context)` hook, which `Application` awaits once the pool is open and before any factory runs — never from core `app/database/init_db.py`, so the plugin still owns its whole vertical. A plugin whose `initialize` raises is added to the exclusion set for tools, commands and prompts alike rather than loading half-working. Deleting the plugin folder leaves its tables behind; accepted, since the database is disposable. A plugin that fails to import, exports no `PLUGIN`, or whose factory raises is logged and skipped rather than taking the process down with it — `TOOL_PLUGINS_STRICT` turns that into a startup failure instead, for a deployment where a silently missing tool is worse than a failed boot. `load_tools()` returns a `LoadedTools` (`tools`, `plugins` that loaded, `failed`), and the failed names join the exclusion set too, so a plugin whose tools did not load cannot still offer its commands or describe its tools in the prompt. The loaded names are what `GET /plugins` reports to the frontend. **A plugin with a UI serves its own HTTP routes** through the optional `ToolPlugin.router_factory(RouteContext) → APIRouter`, in its own `routes.py`: `create_api` calls it once (never in CLI mode, since it runs after `Application.initialize()`) and mounts the router under `/plugins/<name>/`, only for loaded plugins, so an excluded plugin's endpoints return 404 rather than merely being hidden. `RouteContext` carries the `ToolContext` plus the server's own `current_user` and `require_admin` dependencies; every plugin route is mounted with sign-in required, and admin-only is the plugin's choice per route. FastAPI appears only in those `routes.py` files — `contracts.py` names `APIRouter` under `TYPE_CHECKING` alone. Today: `GET /plugins/recruitment/blank/{doc_type}` (moved out of core, which used to import the recruitment plugin to serve it) and `GET /plugins/recycling/catalog`. Two plugins returning a tool of the same name is never survivable, strict or not, and raises immediately: an ambiguous schema is not a condition the model can route around. `EXCLUDED_TOOL_PLUGINS` is an optional denylist for keeping a plugin out of one deployment. Adding a tool is: drop a folder in, restart — there is no runtime reload, because a running conversation's tool set changing mid-turn is not a case this project needs to support.

Today there are three plugins: `app/plugins/clock/` (`get_current_time`, plus `/clock time`), `app/plugins/recruitment/` (`generate_rirekisho` / `generate_shokumu_keirekisho`, plus the entire recruitment vertical described below — named for the business domain rather than for the file format it emits, since the recycling plugin writes files too), and `app/plugins/recycling/` (`recycle_scan` / `recycle_build_catalog` / `recycle_show_catalog`, plus `/recycle` — see below). `read_attachment` used to be a fourth, `attachments`; it is core now (`app/attachments/`, built directly by `Application` ahead of the plugin tools), because every deployment takes uploads and the attachment manifest tells the model to call it unconditionally — excluding it only ever produced a prompt naming a tool that was not there. A plugin owns its whole feature — schemas, renderers, templates, one-off scripts — not just the tool wrapper; the test is that deleting a plugin's folder should remove every trace of the capability and leave nothing importing a package that no longer exists. Nothing a plugin needs but that is genuinely a fact about the application rather than about the feature — `JST`/`today_in_japan()` in `app/utils/jst.py` is the current example — lives outside the plugin instead, since a plugin is never allowed to import another plugin: two plugins needing the same helper is a signal to promote it to application core, not to reach sideways.

**A plugin's model-facing text is split in two, and the split is the point.** `ToolPlugin.system_prompt` — conventionally `load_plugin_prompt(__file__)`, reading a `plugin_prompt.txt` beside the plugin's `__init__.py` — is appended to the persona's system prompt for as long as that plugin is loaded, collected by `load_plugin_prompts()` from the same discovery pass and the same `EXCLUDED_TOOL_PLUGINS` denylist as the tools themselves. That coupling is the whole reason it exists: a standing instruction like "call `read_attachment` again before answering" must disappear from the prompt when the plugin providing `read_attachment` is disabled, and previously it could not, because it lived in the shared `RESPONSE_FORMAT` block sent to every deployment. Everything else a plugin says to the model — tool descriptions, remedies, the messages a tool returns — lives in a `prompts.py` inside the plugin and costs nothing on turns that do not involve it. The dividing question is not "is this prompt text" but "does the model need this before it decides whether to call the tool": only that belongs in `plugin_prompt.txt`.

Two plugins use it today. (The attachments note — contents do not survive a turn, so re-read before answering — used to be the third; it is core now, composed by `app/llm/system_prompt.py` for every prompt set.) `recruitment` contributes something much larger: the interview steps, the pre-generation checks, the two document tools, and the blank forms, all of which used to sit in `app/prompts/anna/system_prompt.txt`. Moving them changed no totals — the same text is sent either way — but it put the knowledge where the capability is, so the persona file now describes only who Anna is and how she behaves, and a deployment that names `recruitment` in `EXCLUDED_TOOL_PLUGINS` no longer tells the model to call `generate_rirekisho`. `recycling` contributes what no single tool description can: that its tools read only the current message's attachments (ask for a re-attach otherwise), that a result table is already on screen and must never be restated, that the catalog tools are called without gatekeeping the user's role (the tool checks; admin and root both count) and a build runs in the same turn, that a force rebuild is never a tool (suggest `/recycle build_catalog_force` and warn it overwrites hand-corrected rows), how to analyse the catalog at scale in SQL with its anomaly checklist, and that edits are one row per call and never unasked — plus the video recording rules (landscape, slow sweep, lights on), which describe this scanner and so must disappear with it. `clock` contributes nothing: its one tool is self-describing. Both still have a `prompts.py` (recycling has two: `prompts.py` at the plugin root for the chat agent — tool descriptions, refusals, post-table summaries — and `pipeline/prompts.py` for what the pipeline sends the vision model) — a plugin contributing nothing to the system prompt still has runtime text worth keeping out of its logic.

There is deliberately **no token budget on plugin prompts**, unlike tool schemas. A tool schema's cost creeps up per plugin folder without anyone deciding to spend it; a `plugin_prompt.txt` is one hand-written file read in full by whoever wrote it, and `recruitment`'s is persona-sized on purpose. The combined size is logged at startup (`Plugin prompts ready | plugins=… characters=… estimated_tokens=…`) so it can be measured, and `SYSTEM_PROMPT_TOKEN_BUDGET` still bounds the total prompt actually sent.

**Slash commands** (`PluginCommand`, `CommandContext` in `app/plugins/contracts.py`; routing in `ChatService.begin_turn`). A command is deterministic: it never reaches the LLM, and its return value — Markdown — is written directly as the assistant message (or a `CommandReply` when its output is display-only and later turns should remember a placeholder instead — see **Reply blocks**). `ToolPlugin.command_factory` is optional and shaped exactly like `factory`: called once at startup with the same `ToolContext`, returning the `PluginCommand`s (`namespace`, an async `handler`, `subcommands`) that plugin claims; `load_commands()` collects them the same way `load_tools()` collects tools, and two plugins claiming one namespace — or two subcommands/aliases within one — raises immediately, exactly like a duplicate tool name. `subcommands` is a tuple of `SubcommandSpec` (`name`, `summary`, `usage`, `attachments`, `aliases`, `admin_only`), the single description of a command: `app/plugins/command_help.py` renders it as the generated `SLASH COMMANDS` block at the top of the plugin prompts (from the commands actually loaded, so an excluded plugin's commands are never described; the block tells the model to call a tool that does the same job rather than point at the command, and that admin-only marks are enforced by the system — admin and root both count — so it must never refuse or question a user over their role; aliases omitted so the model teaches current names), as the reply to an unknown command or subcommand, and as `GET /commands` for the frontend's autocomplete. `ChatService` resolves aliases to the canonical name before the handler runs, answers unknown subcommands itself, and refuses an `admin_only` subcommand for a non-admin (logged at `WARNING`) — enforced once there rather than in each handler, and hidden from non-admins in every listing. Today every catalog command — `/recycle build_catalog`, `build_catalog_force` and `show_catalog` — is admin only: the first two write the catalog every scan depends on, and the third exposes that staff data. `/recycle scan` and `/clock time` are open to every user. A plugin's `plugin_prompt.txt` keeps only what a spec cannot say: when to suggest a command and why. In `begin_turn`, a message whose first whitespace-separated token matches `^/[a-z][a-z0-9-]*$` takes the command path instead of a normal turn — a message that merely contains a slash elsewhere is never hijacked. `namespace` is the plugin name (`/clock`, `/recycle`); everything after it is `subcommand` and `argument`, so one plugin's own `handler` dispatches internally on `subcommand` (`/recycle scan`, `/recycle show_catalog`, ...) rather than the registry knowing about a plugin's individual functions. Identity (`conversation_id`, `user`) comes from `CommandContext`, assembled by `ChatService`, never from `argument` — the same rule `read_attachment` and the document tools already follow. A command still opens and persists a normal turn (both messages, attachments, the conversation log) through the *existing* event path (`message.created`, a terminal event, `complete_message`), so the frontend needs no special handling at all; a handler that raises is caught, logged, and finalized as a `failed` message with a readable error rather than taking the turn or the process down. `TurnIds.is_command` is how the two callers (`server.py`, `cli.py`) know not to also call `ChatService.generate` for a turn `begin_turn` already finalized itself.

**The recycling plugin** (`app/plugins/recycling/`) offers every capability two ways: as agent tools the model calls from plain chat ("scan this video"), and as slash commands a user types. Both run the same runner (`commands.make_recycle_runners`, returning a `RecycleOutcome`); a tool publishes the runner's Markdown as a reply block and gives the model only a summary, so a scan table never passes through the model. Tools: `recycle_scan`, `recycle_build_catalog` (admin, runs immediately — a capture is only readable on its own message, so a confirmation round loses it), `recycle_show_catalog` (admin; posts a link to the catalog page with counts, not the table), `recycle_catalog_health` (admin; also `/recycle health`); `build_catalog_force` is deliberately command-only. **Catalog health** (`health.py`) is tier 1 of the catalog-scale plan: fixed rules in code, no model, the same every run — a name claimed by two rows, near-duplicate labels within a visual_class, weight range inverted or not containing the weight, bounding-box density outside 2–3,000 kg/m³, weight more than 4× from its visual_class median, `volume_m3` larger than its box, a dimension over 10 m, collectable rows missing weight or size, excluded rows with no reason, non-ASCII text. Every threshold is a named constant with its reasoning. It reads rows without building the `Catalog` index (`CatalogRepository.load_items`), because an alias conflict must be *reported*, not raise; it changes nothing; and the report states what it could not check (e.g. no class large enough to compare), so a clean result never overstates its coverage. The model is told to call it first when asked what is wrong, and never to re-implement these rules in SQL — its own part is the plausibility read the rules cannot do. The catalog knowledge tools (`catalog_tools.py`, all admin-only) let the model analyse and edit the catalog: `recycle_query_catalog(sql)` runs one read-only query over the view `recycling_catalog` as the agent database role, and its rows go to the model to reason over; `recycle_create_catalog_item` / `recycle_update_catalog_item` / `recycle_delete_catalog_item` are typed, one row per call — never model-written SQL — validated by the pipeline's own Pydantic models and alias index, with the exact change shown to the user as a reply block. See `app/plugins/recycling/README.md`, **Catalog knowledge tools**. The commands: `/recycle scan [frames]` (one room video or one or more photos; a video goes through `app/utils/video_frames.py`, which drops unusable frames and picks up to 12, then gets the same multi-view scan photos get, and the reply opens with how many frames were used, what was skipped and why, and any capture warnings; `scan_image` / `scan_video` remain as aliases), `build_catalog [frames]` (same input; a video counts as one source in the harvest, so an item filmed across 12 frames is not "seen 12x"), and `show_catalog`. Its `pipeline/` subpackage (`vision.py`, `consensus.py`, `labels.py`, `catalog.py`, `resolve.py`, `build.py`) is the detection pipeline that originally prototyped in a standalone `playground/` folder (now removed — the pipeline only runs inside this app, by design, not as a separate tool: see the TODO doc's §12 for why this is a plugin at all). `vision.py` has bytes-based entry points (`encode_image_bytes`, `detect_items_bytes`) since the plugin gets image bytes from `FileStorage`, and `detect_items_bytes` picks the open-scan or multi-view prompt by image count, so `/recycle scan` deduplicates across several attached photos of one room automatically. `app/plugins/recycling/runner.py` is the async glue the pipeline itself does not have: `consensus.py`'s `detect_stable` and `build.py`'s `harvest` are sequential, blocking loops, fatal for the event loop that also serves SSE, so the plugin fires its consensus runs concurrently via `asyncio.to_thread` and merges them with the pipeline's own unmodified `merge_runs`. The catalog lives in Postgres, in the plugin-owned table `recycling_catalog_items` (`app/plugins/recycling/database/`: one typed column per metadata field, `aliases` as `text[]`, `extra` as JSONB, primary key `(tenant, id)` with a single `'default'` tenant for now). There is no catalog file and no seed: a fresh database starts with an empty catalog, and `/recycle build_catalog` is the only way rows arrive. Each build also records **evidence** (`recycling_catalog_evidence`): which uploaded photo, or which video frame (stored as its own JPEG), each row was detected in — shown as download links in `/recycle show_catalog`'s Evidence column, for a reviewer to see what the model saw. Database failures are logged by `CatalogRepository` and reach the user as a one-line error. Every scan or catalog build also attaches its full structured result as a `text/plain` file on the assistant message — `read_attachment` already reads it, so a follow-up question about a scan still has the complete data on hand even after the conversation has been summarized past what survives in the Markdown reply itself. Slash commands are the first step, not the destination: catalog CRUD and anything needing judgment or a back-and-forth with the user (e.g. confirming a scanned item is really recyclable) is headed toward becoming real tools the agent calls, the same way `generate_rirekisho` is a tool today — commands stay for the parts that must render deterministically, like a scan's own result table. **This plugin must be named in `EXCLUDED_TOOL_PLUGINS` on any deployment of the job-application product** — see the env table above.

**Context assembly** (`app/agent/context/`):

- `SummaryContextBuilder` reads the durable summary and its watermark (`last_summarized_message_id`) — no LLM call.
- `HistoryContextBuilder` reads transcript messages after that watermark, capped at `MAX_CONTEXT_HISTORY_MESSAGES`, and appends an attachment manifest line to each past user message that had one (see **Attachments** below) — one query for every user message in the window, not one per message. Attachments on messages *older* than the first one shown are listed in a block of their own, so they stay readable after summarization.
- `ConversationContextBuilder` composes `[summary_messages, recent_history]` into the `prepared_context` fed to the agent node. Documented extension points: RAG retrieval and durable user-memory facts — the second is specified in [app/agent/context/TODO.md](app/agent/context/TODO.md) as structured per-document slot memory, kept separate from the prose summary because a value that is copied cannot be lost the way a value regenerated by an LLM merge can.

**Attachments** (`app/services/chat_service.py`, `app/agent/context/history_context_builder.py`, `app/utils/attachment_manifest.py`, `app/utils/images.py`, `app/attachments/`). A user can attach images and documents to a message (`POST /conversations/{id}/uploads`, described in the API table above); this section is how the model finds out about them, which is a separate concern from storing them. Every attachment gets one manifest line — `format_attachment_manifest_line` — of the shape `[attachment id=<uuid> name="<filename>" type=<content_type> size=<n>] <note>`, and it is the single place that line is composed, so the turn an attachment arrives on and every later replay of it through history describe it identically. The filename is cleaned (`app/utils/filenames.py`: control and bidi characters removed, brackets replaced) when it is uploaded and again when it is formatted, and JSON-quoted in the line, so a crafted name cannot forge a second manifest line or impersonate the fields after it.

**Supported types** are decided by `app/utils/detect.py` from the bytes, never from the extension: png, jpeg and webp images; pdf; plain text in UTF-8 or Shift_JIS (`cp932`, which is what Windows and Japanese Excel actually write), which covers `.txt`, `.md`, `.csv` and `.json` alike; and video — mp4, QuickTime `.mov`, and Matroska (a `.webm` is reported as matroska, since the two share an EBML header and ffmpeg decodes them identically). Video is accepted by container rather than by codec, and an unknown ISO-BMFF brand is treated as mp4 rather than refused: the camera operator is an untrained customer, so the rule is "accept what ffmpeg can decode". There is no `is_valid_video` to match `is_valid_image` — confirming a video actually decodes is `ffprobe`'s job, and it belongs to the plugin that reads video rather than to the upload path every deployment runs. Office formats are deliberately excluded — a `.docx` or `.xlsx` is mostly tables and layout, and extracting only its paragraphs hands the model half a document without saying so. A row of a type that is no longer accepted is described to the model as unreadable, with an instruction to ask for a PDF or a screenshot.

The turn an attachment is uploaded on is the only turn that can carry its bytes, and even then **image bytes never enter LangGraph state**. `ChatService._build_turn_input` returns a plain-text `HumanMessage` — the user's text plus a manifest line per attachment — and, separately, the image content blocks (only when `LLM_SUPPORTS_VISION` is on): each image turned upright from its EXIF orientation, downscaled to at most 2048px on its long side by `app/utils/images.py`, and base64-encoded. The blocks travel in `config["configurable"]["current_turn_image_blocks"]`, and the agent node joins them onto the message only when it builds each model call's input. The reason is the checkpointer: state is written to Postgres on every graph step and never deleted, so an image inside a message was stored once per step, for every turn compaction kept that message. Config is not persisted — the checkpointer copies only scalar config values into checkpoint metadata, which is why the blocks must stay a list. `LLM_SUPPORTS_VISION` defaults to `false`, since not every model behind `LLM_PROVIDER` understands an image content block; with it off, an image's manifest line says outright that the model cannot see it. Reading and downscaling an image can itself fail — that never fails the turn, only that one image, and its manifest line says the image could not be prepared.

Every later turn, `HistoryContextBuilder` appends the same manifest lines as plain text to each past user message — never bytes, and the line says so explicitly ("visible to you only on the turn it was attached"). Uploads on messages older than the first one in the window — summarized away, or trimmed off an oversized backlog — are listed in a separate system block (`format_earlier_attachments`, newest 30, with a count of any left out), so a file stays readable by id after the message that carried it is gone. The persisted `messages.content` row is never touched by any of this: it stays exactly what the user typed.

Tool results are not persisted to the transcript, so a file the model read last turn is not in front of it this turn — only its own summary of it is. A model treats that summary as knowledge and answers detail questions from it: a test run asked for the third employee's qualification one turn after reading the CSV, made no tool call at all, and returned the second employee's. Two places now say otherwise, because one was not enough: `SYSTEM_PROMPT_SECTION` in `app/attachments/prompts.py` — composed into every system prompt, whichever persona and plugins are loaded — states that attachment contents are not retained between turns and must be re-read before answering, and a manifest line replayed through history says outright that the file has NOT been read in this turn. The cost is one extra `read_attachment` call per follow-up question, which is the right trade against a wrong value reaching a 履歴書.

For a pdf or text attachment the manifest line's note is an instruction to call `read_attachment`. That tool (`app/attachments/tools.py`) verifies the requested id belongs to the conversation in `config["configurable"]["thread_id"]` before touching it, exactly like `recruitment/tools.py`'s identity check, and returns a not-found message for an id that does not resolve — the id is model-supplied. Extraction (`pypdf` for pdf, `detect.decode_text` for text) runs in `asyncio.to_thread`, and every failure is reported back to the model as text rather than raised. Three PDF cases get their own message, because each needs the model to ask the user for something different: a password-protected file; a file with no text at all, which is almost certainly scanned; and a file where only some pages have text, which gets a note on every page of output so the model does not answer from a typed cover page as if it were the whole document. For the scanned cases the model is told to ask for screenshots when vision is on, or for the content to be pasted when it is off. The extracted text is paginated at roughly 8,000 characters, and the response states which page came back and how many exist. An image's `read_attachment` response is metadata only.

**Conversation titles** (`app/services/conversation_title_service.py`): a new conversation is created with the placeholder title `New Conversation`. On the first `ChatService.begin_turn`, a background task (`ConversationTitleService.generate_and_store`, spawned from `begin_turn` so it never adds latency to the turn) asks the LLM for a short title from the user's message and writes it, then publishes `conversation.updated` — the same event a turn already emits, so the sidebar refetches the list and the title appears while the answer is still streaming. The service re-reads the conversation and does nothing unless the title is still the placeholder, which is what makes it safe to spawn on every turn and what stops a later turn, or a manual rename, from being overwritten. The instruction comes from the prompt set's optional `title_prompt.txt` or the built-in `DEFAULT_TITLE_PROMPT`; output is stripped of quotes and label prefixes and capped at `TITLE_MAX_CHARS`. `PATCH /conversations/{id}` sets the title by hand (owner or admin, `{"title": "…"}`, same cap) and publishes the same event; the UI renames inline via a pen button that appears on the sidebar row.

**Summarization** (`app/services/summarization_service.py`): after each completed turn, `ChatService` schedules `SummarizationService.trigger_if_needed`. It reads the summary state **once** and threads that snapshot through the whole run, estimates tokens (`len(text) // 4`) over messages not yet summarized and, if over `SUMMARY_TOKEN_THRESHOLD` (or `MAX_UNSUMMARIZED_MESSAGES` is exceeded), generates a chunk summary via the LLM, merges it into the existing summary via a second LLM call, and advances the watermark. No pooled connection is held across either LLM call.

Not every unsummarized message is folded. `_split_for_retention` holds back the last `MIN_RETAINED_RAW_MESSAGES`, and the watermark advances only as far as what was actually summarized, so the turn after a summarization still sees recent messages verbatim instead of a paraphrase and nothing else. Without that tail the model loses the thread at exactly the point summarization runs — re-asking questions the user has already answered and re-proposing text it has already had approved. The retained slice is extended backwards to the nearest user message so it opens with a question rather than half of an answer; if that alignment would consume the whole backlog, the unaligned split is used instead, because a watermark that never advances is the worse failure.

The merged summary is bounded twice. The merge prompt is given a length budget of 75% of `MAX_SUMMARY_CHARS` along with an explicit trim order, so the model decides *what* to lose; `_cap_summary` then truncates anything still over `MAX_SUMMARY_CHARS` and logs a warning. The prompt is for quality, the cap is the guarantee — the gap between the two is what keeps that warning meaningful rather than routine.

The write goes through `SummaryRepository.save_summary_chunk_and_advance`: the state upsert and the chunk insert commit in one transaction, and the upsert is **conditional** on the watermark still being where the caller read it (`WHERE last_summarized_message_id = %s`). A run whose watermark moved underneath it rolls back and returns `False` instead of writing a duplicate chunk. `ChatService._summarizing` is the cheap in-process guard that avoids the wasted LLM call in the common case; this check is the correctness backstop, and the only one that would survive more than one worker process. The updated summary is never written into LangGraph checkpoint state; it is read back from PostgreSQL by `SummaryContextBuilder` on the next turn.

**Document generation** (`app/plugins/recruitment/`, `app/storage/`, `app/repositories/file_repository.py`). Three layers, each ignorant of the ones above it. `app/plugins/recruitment/schemas_rirekisho.py` and `app/plugins/recruitment/schemas_shokumu.py` are the Pydantic contracts, one per document type — `Rirekisho` and `ShokumuKeirekisho` with their nested types — and each doubles as its tool's `args_schema`, so every field description is prompt text the model reads on each call. `schemas_shokumu` imports `YearMonth` and `KANA_PATTERN` from `schemas_rirekisho` rather than restating them: both documents carry the same person's name and the same 年月 pairs, and a rule that accepted a value on one document while rejecting it on the other would be a confusing bug to hit. A `Renderer` (`app/plugins/recruitment/renderers/`) knows a schema and a template and nothing else: no database, no storage, no LLM. That narrowness is what let the `.txt` renderer the schemas were developed against be swapped for `XlsxRenderer` and `DocxRenderer` by changing one argument each in `tools.py`. A `FileStorage` (`app/storage/`) holds bytes; `LocalFileStorage` is the development backend, writing to `FILE_STORAGE_DIR` under date-prefixed keys (`2026/09/04/<uuid>.xlsx`) that map directly onto S3 object keys later. Alongside `write`, it offers `write_stream` for bodies too large to hold in memory (a 150 MB video buffered and then copied peaks near 300 MB) and `temporary_path`, an async context manager yielding a local path for the consumers that cannot work from bytes — ffmpeg needs a seekable file. `temporary_path`'s contract is "a temporary local copy", not "where the file lives": the local backend yields the real path and copies nothing, while an S3 backend would download and delete, which is where the wording earns its keep. The storage layer generates its own keys and a caller cannot supply one, so a model-supplied filename can never reach a filesystem path — path traversal is impossible by construction rather than by validation. Writes go to a temporary name and are renamed into place, so a crash mid-write leaves a stray `.part` file rather than a truncated document that looks complete.

`generate_rirekisho` and `generate_shokumu_keirekisho` (`app/plugins/recruitment/tools.py`) are built by one closure factory with those dependencies bound in, for the same reason as `make_current_user`: reaching for module globals would make the graph impossible to construct twice. `app/plugins/recruitment/__init__.py` is the thin layer that exposes this factory to the plugin loader as a `PLUGIN` — the vertical's only concession to being a plugin at all. Every document type validates, renders, stores and records its file the same way — only the schema, template and `document_type` differ — so that body was factored into a single builder once a second document made the duplication real rather than hypothetical. Each tool re-validates its arguments through its schema even though LangChain already checked them against `args_schema` — that second pass is what turns a dict back into a typed object, and the only guarantee that what gets rendered is what passed validation. Identity comes from the run configuration (`thread_id`, `assistant_message_id`), never from the tool arguments, since a conversation id supplied by the model could name someone else's conversation. The run configuration also carries the authenticated `user` (set by `ChatService.generate` from the session, passed through `AgentGraph.stream`); a new tool reads all of it through `app.plugins.run_identity(config)`, which returns a typed `RunIdentity` (`conversation_id`, `user`, `is_admin`, `user_message_id`, `assistant_message_id`, and `command_context(subcommand)` so a tool can reuse a slash command's handler unchanged) and fails closed when a key is missing. Tools are bound once at startup and every user sees every tool, so an admin-only tool checks `is_admin` itself. **Reply blocks** (`app/services/reply_blocks.py`) are how a tool gets Markdown to the user exactly, bypassing the model: `ChatService.generate` attaches a writer for the assistant message it is generating, the tool calls `ToolContext.reply_blocks.publish(assistant_message_id, markdown)`, and the block goes into the same buffer and `message.delta` stream as the model's tokens — as its own paragraph, saved in the message where it appeared, no frontend change. The tool then returns only a short summary to the model. **Opt-in:** a tool that never calls `publish` is unaffected, and most should not — the document tools, `get_current_time` and `read_attachment` return to the model as before. Use a block only when dropping or rewording the output would matter (a scan table, the catalog listing); a generated file already reaches the user exactly, as an attachment. `publish` returns `False` when no generation is attached, and must be called from the event loop (an async tool). Framework-free on purpose: LangGraph's custom stream writer would do the same, but would tie reply composition to its streaming API. **Display-only blocks:** a block is saved into the assistant message, and the saved message is what every later turn loads as history — so a large block would ride along in every later turn's context. `publish(..., context="one-line placeholder")` marks a block display-only: `ChatService` keeps two buffers, and saves the placeholder version as `messages.context_content` (migration 5). A slash command does the same by returning `CommandReply(content, context_content=...)` instead of a str. The display reader (`get_messages`) returns `content`; the model-history and summarization readers select `COALESCE(context_content, content)`. `/recycle show_catalog` (command and tool) uses it: the user sees the whole table, later turns see one line pointing at `recycle_query_catalog`. Bytes are written before the row, because the reverse order can produce a row pointing at a file that does not exist — which the user meets as a failed download — while this order can only leave an unreferenced blob. The string returned to the model is terse and forbids it from writing a link of its own: told only that a file "is attached", a model will construct a plausible download path around the filename, and an early test run produced `sandbox:/mnt/data/…`, a convention from its training data that points nowhere here. The real download comes from the message attachment, so any link the model writes is broken by construction.

**Filling the 履歴書 form** (`app/plugins/recruitment/renderers/xlsx_renderer.py`, `app/plugins/recruitment/layouts/rirekisho_jis.py`, `app/plugins/recruitment/renderers/ooxml.py`). The form is filled, never built: its ruling, 96 merged ranges, column widths, print setup and 写真を貼る位置 box come from a template workbook a person made in Excel, and the renderer only writes text into cells that already exist. `layouts/rirekisho_jis.py` is the cell map, transcribed from the real file rather than computed — the ruling is irregular (`D28:I29` spans two rows, `D34:I34` spans one), so an anchor list is the only description that is actually true of it. openpyxl reproduces cells, styles, merges and page setup exactly but does not model DrawingML shapes, so saving silently drops the photo box; `ooxml.restore_drawings` copies that part back into the saved package, along with the worksheet relationship, the `<drawing>` element and the content-type override that a valid package needs. `app/plugins/recruitment/scripts/make_rirekisho_template.py` builds the blank template from the approved sample by clearing exactly the cells the applicant filled — a plugin-local script, run by hand, not part of the loaded application.

Capacity is the interesting constraint. A printed 履歴書 has as many ruled lines as it has, so the layout module measures text in the half-width units Excel uses for column width and applies two caps: text that overflows a region steps the font down, and text that still overflows at the smallest readable size raises `LayoutOverflow`. Shrinking silently is fine — the reader sees smaller text. Truncating silently is not, because this document goes to an employer and a half-printed company name is worse than a generation that failed and asked a question. `LayoutOverflow` and the row-count checks are written in Japanese and phrased as guidance, because they reach the assistant through `ToolNode`'s error handler and become the question it asks the user ("this is more rows than the form holds — shall we merge the 入社 and 退職 lines?").

**Filling the 職務経歴書** (`app/plugins/recruitment/renderers/docx_renderer.py`). None of that applies here: a `.docx` flows and paginates itself, so there is no slot map, no capacity budget and no overflow to raise. The renderer instead flattens each section into a list of lines and hands them to a docxtpl template that loops over them with a single tag. All the branching that decides what a section says therefore lives in Python, where it can be read and tested, rather than as three template paragraphs per optional field — which is also why an empty section renders as nothing at all instead of a heading over an empty table. `app/plugins/recruitment/scripts/make_shokumu_template.py` builds that template from the approved sample, keeping its page size, margins, footers, MS 明朝 at 10pt and table ruling, and replacing the sample's text with tags.

The four approved 職務経歴書 references disagree with each other — on whether they carry ■PCスキル or ■資格, on how many 自己PR blocks they argue, on whether the job table has side columns. Every difference is a *presence* difference rather than a structural one, so the schema holds the union and the template renders one shape whose sections appear only when populated.

Validators enforce *format*, never completeness: every one returns early on an empty value, because a blank field means the user chose not to supply it, and a 履歴書 printed with blanks is a normal way to use the form. Only a value that is present and malformed is an error. Furigana is the case where that distinction has teeth — `name_kana` is kana-only, but `address_kana` also accepts digits and hyphens, since Japanese address furigana carries block numbers as numerals (`しんじゅく3-12-8`) rather than transcribing them phonetically. Applying the name rule to the address rejected correct input and pushed users into dropping real information to satisfy the validator.

Dates are stored as 西暦 and converted only when rendered. The application-wide fact — `JST`, `today_in_japan()` — lives in `app/utils/jst.py`, since the clock plugin needs it too and a plugin may never import another plugin's internals; the document-specific formatting — `to_japanese_era`, `to_japanese_era_year`, `age_on` — stays in `app/plugins/recruitment/dates.py`. Chronological ordering and the birth-date check both need a monotonic year, and 平成/令和 are a presentation of that year rather than a different fact — so nothing upstream of a template knows about eras. Age is derived the same way, from `birth_date` and the document's own date, which is why it is not a schema field: it is a fact about the rendered document, not about the applicant, and a field would invite the model to invent one. The 和暦 helpers currently have no caller — the chosen 履歴書 layout prints 西暦, as both of the client-approved samples using that form do — and are kept for the alternative layout that does. A `HistoryEntry` may also omit its `period` entirely, for the final ongoing row a 履歴書 writes as 現在に至る; the validator allows that only as the last row, since a dateless entry means "still true" and cannot precede one that ended.

**Connection configuration** (`app/config/settings.py`). The database is addressed one of two ways. If `DATABASE_URL` is set, it is the source of truth — the full libpq connection string, so it can carry `?sslmode=require` and anything else a managed Postgres needs — and `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` are parsed back out of it with `psycopg.conninfo.conninfo_to_dict` (a few callers need a part on its own: `create_db_if_not_exist` needs the database name to test for and create it). If `DATABASE_URL` is not set, it is assembled from those `DB_*` parts, with the password percent-encoded. Either way both `DATABASE_URL` and every `DB_*` name end up populated and consistent, so a caller uses whichever it needs — the async pool and the LangGraph checkpointer take the URL, `get_connection` takes the URL, and `create_db_if_not_exist` takes the URL with `dbname` overridden to `postgres` so it can reach the server before the target database exists. A `DATABASE_URL` with no database name fails at startup.

**Agent database role** (`app/database/agent_role.py`, `ToolContext.agent_role`). SQL the model writes never runs on the application's pool: that logs in as `DB_USER`, a superuser locally, and could read `users` and `sessions` or rewrite anything. `AgentRole` owns a separate LOGIN role (`DB_AGENT_USER`) with **no table grants**, and a small pool (max 2) that logs in *as* it — a separate login, never `SET ROLE` on the main pool, since a superuser session can always `RESET ROLE` back and the model's SQL could do it. Plugins grant their own tables or views with `agent_role.grant_select(relation)` from their `initialize` hook, so core never knows what plugins store and a plugin can only open up what it owns. The role is created **lazily**, on the first grant — a deployment where no plugin asks (the job-application server, which excludes `recycling`) never gets a login role it does not use. It is refused if it equals `DB_USER` or already exists with superuser/createrole/createdb/bypassrls; otherwise its password is re-applied every start and its session defaults set to read-only with a 5 s statement timeout. It is not given the `SUPERUSER` attribute by name even to deny it, because on RDS the master user may not name it. `agent_role.query(sql, max_rows=)` is the only way model-written SQL runs. The grants are the guard; behind them, each layer measured against a real server: the SQL is wrapped as `SELECT * FROM (<sql>) AS agent_query LIMIT n+1` (a second statement becomes a syntax error, a data-modifying `WITH` is refused inside a subquery, `SET` is rejected, and the row cap applies inside the database so a 10k-row table costs nothing extra), in a `READ ONLY` transaction with `SET LOCAL statement_timeout`, sent with `prepare=True` (Parse refuses multiple statements), with no parameters so a `%` in the model's `LIKE` is sent as written. `AgentQueryResult.as_text(max_chars)` renders the rows for the model, spells `NULL` out, and states when the row or character cap cut the result. A failed query is logged at WARNING (the model writing a bad query is expected) and returned as `AgentQueryError` for the model to correct.

**Persistence** — two separate stores:
- Application data (PostgreSQL, `app/database/`, `app/repositories/`): `users`, `sessions` (opaque session tokens, stored as SHA-256 hashes), `conversations` (each owned by a user, with a lifecycle `status`), `messages` (`content` as displayed; `context_content` when later turns should remember something shorter), `conversation_summary_state` (current summary + watermark), `conversation_summaries` (historical chunk log), `files` (both agent-generated documents and user uploads, distinguished by `origin`; metadata and a storage key, cascading from conversation, message and user — `message_id` is nullable because an upload exists before the message it attaches to; the bytes themselves live in `FileStorage`, not in the database), `app_settings` (sparse key/value store of persisted runtime-setting overrides). Tables are created on startup if missing; `app/database/migrations.py` applies versioned schema changes to tables that already exist (tracked in `schema_migrations`), since `CREATE TABLE IF NOT EXISTS` cannot. Every repository (`app/repositories/`) is async and reads/writes through one shared `psycopg_pool.AsyncConnectionPool`, returning typed dataclasses (`psycopg.rows.class_row`) rather than positional tuples.
- LangGraph checkpoint state: managed separately by `AsyncPostgresSaver` (`app/agent/checkpointer.py`) for graph replay/resumption. It opens its own connection independent of the application pool.

**Realtime** (`app/runtime/event_bus.py`, `app/runtime/conversation_lock.py`):
- `EventBus` is in-process pub/sub, keyed by conversation. `publish()` is synchronous and never blocks, so a slow subscriber cannot stall generation; each subscriber holds a bounded `asyncio.Queue` (`SSE_QUEUE_MAXSIZE`) and is dropped rather than buffered without limit if it falls behind. Event types: `message.created`, `message.delta`, `message.completed`, `message.cancelled`, `message.failed`, `conversation.updated`.
- `ConversationLock` is an in-process `dict`-backed lock serializing generation per conversation. Correct without a `Lock`/mutex only because acquisition never awaits between the membership check and the insert.
- Both are process-local. A multi-worker deployment would need `LISTEN/NOTIFY` (event bus) and a PostgreSQL advisory lock (conversation lock) instead — the interfaces are kept narrow enough that this is a swap, not a rewrite.

**Logging** (`app/utils/logger.py`, `app/utils/conversation_log.py`). One named logger (`llm_app`) writing a daily rotating file under `app/logs/`, optionally mirrored to the console. Third-party libraries log to their own loggers and never propagate into it, so `LOG_LEVEL=DEBUG` yields this project's own tracing rather than a firehose.

`CONVERSATION_LOG=true` attaches a second handler writing `app/logs/{date}_conversation.log`: the turn-by-turn transcript, each tool call's arguments as indented JSON (`ensure_ascii=False`, so Japanese is readable rather than escaped), and the graph's node transitions — enough to see exactly what the model received and what it passed to a tool. Two filters keep the two files apart and both are necessary. `_RootConversationFilter` admits only the root user's turns, and only from the four modules that describe a turn, matched on `LogRecord.module` because every module shares the one logger. `ExcludeConversationContent` does the opposite job on the daily log and the console: without it, `LOG_LEVEL=DEBUG` would copy every name, address and phone number the user typed into a second file whose handling nobody reasoned about.

The acting user reaches those filters through a `ContextVar` set in `ChatService.begin_turn`. asyncio copies the current context into every task it creates, and `begin_turn` is awaited rather than spawned, so the value lands in the caller's context and is inherited by the spawned generation task, the graph run inside it, and each tool call — without threading a parameter through any of them, in either the CLI or the API. The logger itself sits at `DEBUG` whenever conversation logging is on, purely so those records can reach that handler; every other handler carries `LOG_LEVEL` as its own level, which is also why `set_log_level` applies a runtime change per handler instead of to the logger — lifting the logger would silently switch the conversation log off.

**Frontend** (`ui/src/`): React 19 + TypeScript on Vite, with TanStack Query used only as a cache for the two REST resources — it is deliberately absent from the streaming path.

The selected conversation lives in the URL (`/c/:conversationId`), so a refresh, a bookmark and a second tab all resolve to the same conversation. `ChatPage` reads that route parameter and wires four hooks, all keyed by it:

- `useConversations` — the sidebar list, plus creation and cache invalidation. Also exports `useConversationsRefresh`, the seam that lets the event stream mark the list stale without importing a cache library.
- `useMessages` — the persisted transcript, plus `useMessageCache` giving the stream write access to it. No writer ever invents a row: an event about a message that is not cached triggers a refetch instead.
- `useConversationStream` — one `EventSource` per conversation, tied to the conversation rather than to sending, because the server treats the sender as an ordinary subscriber. Tokens accumulate in a ref and are published to React state once per animation frame, so rendering is decoupled from the model's output rate. Its state carries the conversation id it belongs to, which makes a conversation switch a comparison during render rather than a reset effect.
- `useChat` — sends a turn and reports why one was refused. It owns no message state: the user's own message arrives back over the event stream like everyone else's, so there is one rendering path rather than two.

`Chat.tsx` renders each message as `drafts[id] ?? message.content` — while a turn is in flight the database row is still empty and the text exists only on the wire; the terminal event writes the authoritative content and drops the draft, so the fallback resolves itself. Below the text it renders `message.attachments` as download links to `GET /files/{id}`. A message announced by `message.created` cannot have files yet, so the stream inserts it with an empty list rather than guessing; attachments arrive with the persisted row.

Assistant messages are rendered through `Markdown.tsx`; user messages are not, so a user typing literal `**` sees it unchanged. A ```` ```mermaid ```` fence is diverted to `MermaidDiagram.tsx` and drawn as SVG. Because content streams in token by token, a fence is incomplete for most of an answer, and a half-typed diagram never parses — so `Chat.tsx` passes an `isStreaming` flag down and mermaid is not called at all until the message finishes. When it is called, `mermaid.parse({ suppressErrors: true })` validates first: it is `render()` on invalid input that leaves orphaned error graphics in `<body>`, which accumulate faster than they can be cleaned up and only a full page reload clears. Unclosed Markdown resolves itself once the closing marker arrives.

Recovery is deliberately simple. Deltas are not replayable, so the stream re-reads the transcript on every connect and reconnect, and a client that joins mid-generation renders partial text until the terminal event delivers the full content. That is the entire answer to a dropped connection — no `Last-Event-ID`, no server-side replay buffer.

**Frontend plugins** (`ui/src/plugins/`) are the UI half of backend plugins, and follow the same rule: a plugin owns its vertical — components, CSS, and its own strings, merged into i18n under `plugins.<name>` — and core never imports a plugin folder, it only renders *slots*. A `FrontendPlugin` is `{name, messages?, chatSidebar?}`; `name` is the backend folder name exactly. `plugins/index.ts` lists the plugins bundled into the app, but bundled is not shown: `usePlugins()` keeps only those `GET /plugins` lists, so `EXCLUDED_TOOL_PLUGINS` stays the one switch for both halves. That gate fails *closed* — nothing shows until the server answers — the opposite of the backend's denylist, because here a wrong yes displays a feature the deployment excluded. Hiding is presentation only; a plugin's endpoints refuse on their own, and an excluded plugin's routes are not mounted at all. A plugin calls its endpoints with the exported `request()` from `api/client.ts`, from its own folder. Three slots exist, added as a plugin needed each:
- `chatSidebar` — rendered in the chat sidebar (recruitment's blank forms).
- `settingsSections` — pages under the PLUGIN category at `/settings/plugin/<name>-<id>`; the plugin cannot pick the category, so it can neither sit among core sections nor collide with another plugin. `SettingsPage` waits for `/plugins` before redirecting, or a deep link to a plugin page would bounce to the first core section.
- `commandRedirects` — a typed slash command the frontend answers by opening one of those pages instead of sending it: `/recycle show_catalog` opens the recycling catalog browser. Matched the way `ChatService` splits a command, bare form only (no argument, no attachments), and only for a user who may see the page; anything else is sent as usual, so the backend's own refusals still apply. The assistant's `recycle_show_catalog` tool points at the same page from the other side: it posts a link to it (with counts) instead of a table. `Markdown.tsx` follows any root-relative link through the router, so opening it does not reload the app.

`App.tsx` also routes `/settings/:category/:sectionId` to `SettingsPage.tsx`, the admin UI over the runtime settings described above; bare `/settings` redirects to the first section the user may see. The page is a shell (navbar, a sidebar of sections, the open section) over one list, `SETTINGS_SECTIONS` in `ui/src/settings/sections.ts`: each entry names a category (who owns it — `core`, `root`, `plugin`), a `minRole` (who sees it; presentation only, the backend refuses regardless), and a component. The four CORE sections share `RuntimeSettingsForm`, which saves a section as one `PATCH` batch — several settings constrain each other and the server checks the merged result, so saving them one at a time can pass through a rejected state — and shows a `422`'s reason verbatim, since the cross-field rules live only on the server. The form is `noValidate` for the same reason: one validator, not two. The persona is a dropdown over `GET /settings/prompt-sets` rather than free text, because an incomplete or misspelled set is accepted and silently runs as `default`.

Authentication is a gate around the whole app rather than a route. `AuthProvider` (`ui/src/auth/`) holds one TanStack Query entry for `GET /auth/me` whose query function swallows a `401` into `null`, so "not logged in" is data rather than an error; `AuthGate` renders `AuthPanel` or the app from it. `AuthPanel` is the whole signed-out screen and toggles between `LoginPage` and `SignUpPage` in local state, since `BrowserRouter` is mounted below the authenticated boundary and the signed-out screen has no routes of its own. A session that expires mid-use is caught in one place: the provider subscribes to the query and mutation caches and flips the auth entry to `null` on any `401`, so every screen reacts to a lost session without a single component checking for it. Signing out clears every cached query except the auth entry itself, so the next user never sees the previous one's conversations. `api/client.ts` sends `credentials: "include"` on every `fetch` and `useConversationStream` opens its `EventSource` with `withCredentials: true`, which is what carries the `HttpOnly` cookie onto the event stream.

The context is split across two files on purpose — `AuthContext.ts` exports the hook and context, `AuthProvider.tsx` exports only the component — because a module exporting both a component and non-components defeats React Fast Refresh, which ESLint's `react-refresh/only-export-components` rule enforces.

**Localisation** (`ui/src/i18n/`). Interface text is localised with `i18next` and `react-i18next`. The catalogues are two typed modules: `locales/en.ts` defines the shape and `locales/ja.ts` is typed against it (`Messages = typeof en`), so a key added on one side without the other fails `tsc` — there is no runtime "missing translation" state to notice. `index.ts` initialises i18next synchronously from those bundled resources (`useSuspense: false`, since nothing ever loads lazily) and is pulled in for its side effect by `main.tsx` before the first render. Japanese is the default because the app is used mostly from Japan; there is deliberately no locale or geolocation detection, only an explicit choice persisted to `localStorage` under `lang` and mirrored onto `<html lang>` for accessibility. `LanguageSwitcher` — a Bootstrap dropdown with a globe icon, reusing the navbar's `.theme-toggle` button style — sits in the navbar for the signed-in app and is pinned to the corner of `AuthPanel` for the signed-out screen, which has no navbar. The auth pages, navbar, sidebar and chat chrome are translated; the "LLM System" wordmark, the 履歴書 / 職務経歴書 form names, and server-supplied error strings (`ApiError` detail) are left as they come. Assistant message content is the model's own output, not interface text, so it is unaffected by the switch.

**LLM** (`app/llm/`). `llm_factory.py` holds a provider registry and returns a LangChain `BaseChatModel`, so the rest of the codebase never names a vendor. `ollama_llm.py` builds `ChatOllama`; `openai_llm.py` builds `ChatOpenAI` and accepts a custom `base_url`, which covers OpenRouter, Groq, DeepSeek and anything else speaking the OpenAI Chat Completions API. An unknown `LLM_PROVIDER` fails at startup with the list of valid values. `system_prompt.py` loads the persona from the prompt set named by `SYSTEM_PROMPT` (`app/prompts/<name>/system_prompt.txt`); set resolution lives in `config/prompts.py` and is all-or-nothing, so an incomplete folder falls back — persona included — to the `default/` set, and an unreadable `default/` degrades to a built-in prompt rather than failing startup. `load_first_message` reads the same set's optional `first_message.txt`; the `POST /conversations` handler seeds it as a complete `assistant` row in the conversation's own transaction, so the persona opens with a stated direction. `load_title_prompt`, `load_summary_chunk_prompt`, and `load_summary_merge_prompt` do the same per-run resolution for the other set files, so every prompt in a set follows a runtime `system_prompt_name` change — not just the persona. Every persona, including that fallback, is composed with a shared `RESPONSE_FORMAT` block describing what the frontend can render (Markdown, mermaid, no LaTeX or raw HTML). That contract belongs to the interface rather than to any one persona, so it lives in code instead of being duplicated across prompt files — and for the same reason it contains nothing about any plugin, however true that would be of the current deployment: an instruction to call a tool that is not loaded is simply false, so plugin text arrives separately, as the `plugin_prompts` argument `load_system_prompt` appends under its own `YOUR TOOLS` header (see **Tool plugins**). It is threaded from `Application.initialize()` through `AgentGraph` to the agent node rather than read from a module global, because which plugins are loaded is a property of one `Application` instance. The composed prompt is measured against `SYSTEM_PROMPT_TOKEN_BUDGET` and logs a warning when it exceeds it — a warning rather than an error, because a long prompt still works and this module's contract is to degrade rather than block startup.

## API (`--api` mode)

Every route except `GET /health`, `POST /auth/login`, and `POST /auth/register` requires the session cookie. Conversation, message, and event routes are scoped to the authenticated user; a conversation owned by someone else is reported as `404`. Every non-safe method (anything but `GET`/`HEAD`/`OPTIONS`) also passes the CSRF middleware: a bad or missing `Origin`, a form `Content-Type`, or a missing/invalid `csrf_token` cookie + `X-CSRF-Token` header pair is a `403` (see **Authentication** above).

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Public, unauthenticated. Borrows a pooled connection and runs `SELECT 1`: `200 {"status":"ok"}` when the process is up and the database is reachable, `503` otherwise. For a load balancer or orchestrator target check |
| `POST` | `/auth/register` | Public. Body: `{"email": str, "password": str}`. Creates a `user`-role account and returns `{id, email, role}` with `201`; `409` if the email is already registered. Sets no cookie — the client calls `/auth/login` next |
| `POST` | `/auth/login` | Body: `{"email": str, "password": str}`. On success, sets the `HttpOnly` session cookie and the readable `csrf_token` cookie, and returns `{id, email, role}`; `401` on bad credentials |
| `POST` | `/auth/logout` | Deletes the current session and clears the session and `csrf_token` cookies. `204` |
| `GET` | `/auth/me` | The current user as `{id, email, role}`, or `401`. Also re-issues the `csrf_token` cookie, so a full page load repairs a stale one |
| `POST` | `/conversations` | Create a conversation owned by the caller |
| `GET` | `/conversations` | List the caller's conversations (each includes a lifecycle `status`: `active` / `held` / `closed`) |
| `GET` | `/conversations/{id}/messages` | Get a conversation's transcript (includes `status` per message: `streaming` / `complete` / `interrupted` / `cancelled` / `failed`) |
| `POST` | `/conversations/{id}/messages` | Open a turn and start generating in the background. Body: `{"client_message_id": UUID, "message": str}`. Returns `202` with `{user_message_id, assistant_message_id}` immediately — the response is not in this call, only over `GET /events`. `client_message_id` is an idempotency key: a retried send with the same key returns the original ids (`200`) rather than generating a second answer. A second concurrent send on the same conversation while one is in flight gets `409` with the in-flight `assistant_message_id`, so the caller can subscribe to it instead. A send into a conversation an admin has put on hold gets `423` |
| `POST` | `/conversations/{id}/uploads?filename={name}` | Store one attachment, before it is attached to any message. Raw body (not multipart), streamed and capped at `UPLOAD_MAX_BYTES` — `413` if exceeded. `filename` is a percent-encoded query parameter, since it may be Japanese and headers are latin-1. `Content-Type` is never trusted: the actual type is read from the bytes (png/jpeg/webp/pdf, UTF-8/Shift_JIS text, or mp4/mov/matroska video; anything else, or an image that fails to decode, is `415`). The filename is stored cleaned (see **Attachments**). Returns `201` with `{id, filename, content_type, size_bytes}` |
| `GET` | `/events?conversation_id={id}` | Server-sent events (`text/event-stream`) for one conversation. Any number of clients may subscribe and all receive the same stream, which is what keeps multiple tabs on the same conversation consistent |
| `GET` | `/files/{file_id}` | Download a generated document or an uploaded attachment. Scoped to the owning user (admins may read any); someone else's file is reported as `404`, not `403`, so an id they cannot see is never confirmed to exist. A row whose bytes are missing is logged at `ERROR` — that is our inconsistency, not a bad request — but still answered `404` |
| `GET` | `/plugins` | `{"plugins": [...]}`: the tool plugin folder names this deployment loaded (excluded and failed ones absent). The frontend shows a plugin's UI only when it is listed |
| `GET` | `/plugins/recruitment/blank/{doc_type}` | An empty 履歴書 (`rirekisho`) or 職務経歴書 (`shokumu_keirekisho`), rendered on demand. Recruitment plugin; 404 when it is excluded |
| `GET` | `/plugins/recycling/catalog` | One page of the item catalog with each row's evidence (`search`, `visual_class`, `excluded`, `offset`, `limit` ≤ 200). **Admin only.** Recycling plugin; 404 when it is excluded |
| `GET` | `/commands` | The slash commands this deployment loaded, as `{"commands": [{namespace, subcommands: [{name, usage, summary, attachments, aliases, admin_only}]}]}`, for the frontend's autocomplete. Admin-only subcommands are omitted for non-admins (they are refused on send regardless) |
| `GET` | `/settings` | Every runtime-adjustable setting with its live value, whether it persists, and its environment default |
| `PATCH` | `/settings` | Apply a batch of setting changes (`{key: value}`). **Admin only.** `422` on an unknown key or invalid value |
| `DELETE` | `/settings/{key}` | Reset one setting to its environment default, dropping any persisted override. **Admin only** |
| `GET` | `/users` | Every account (`id`, `email`, `role`, `created_at`, `updated_at`), root first. **Root only** |
| `POST` | `/users` | Create an account `{email, password, role: user\|admin}`. `201`; `409` if the email is taken. **Root only** |
| `PATCH` | `/users/{id}` | Change any of `{email, password, role}`; a new password signs the user out everywhere. `409` for the root account or a taken email. **Root only** |
| `DELETE` | `/users/{id}` | Hard-delete an account and everything it owns (cascade), then its stored files' bytes. `204`; `409` for the root account. **Root only** |
| `GET` | `/settings/prompt-sets` | Names of the complete prompt sets under `app/prompts/` (the settings page's persona choices) |

CORS is restricted to `CSRF_TRUSTED_ORIGINS` (default `http://localhost:5173`, the Vite dev server for `ui/`), with `allow_credentials=True` so the browser sends the session cookie. The same list drives the CSRF middleware's `Origin` check, so the two cannot drift apart.

## Deployment

`deploy/` holds everything for running this in a server environment: the backend `Dockerfile`, a local `docker-compose.yml` and a production `docker-compose.prod.yml`, and the host `nginx/llm-system.conf` that serves the built SPA and reverse-proxies the API routes to the container on a single origin. `.github/workflows/deploy.yml` is a CI/CD pipeline that builds and pushes the image, ships the SPA and nginx config, and releases over SSH on a push to the `deploy` branch (or a manual run against `main`).

The current target is a single EC2 instance with an external (RDS) PostgreSQL, reached by the instance's public IP over plain HTTP — a throwaway environment for client evaluation. **[deploy/README.md](deploy/README.md)** is the runbook: topology, the server-side `.env` deltas, release and rollback, the one-time secret setup, and the accepted risks (SSH open to the world, no TLS) that are deliberate for this environment and must not be "fixed" without moving the whole deployment off a bare IP first.
